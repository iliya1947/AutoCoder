# AutoCoder — AGENTS.md

Корневые инструкции для coding agents, работающих с репозиторием AutoCoder.

Этот файл действует на весь репозиторий. Более глубокий `AGENTS.md` может добавлять локальные правила для своего поддерева и имеет приоритет только в своей области.

## 1. Источники истины

Перед существенной задачей прочитай:

- `Doc/PROJECT_MEMORY.md` — конечная цель, целевая архитектура и устойчивые инварианты;
- `Doc/PROJECT_STATE.md` — фактически реализованное состояние, проверки, известные проблемы и текущий этап;
- релевантный более глубокий `AGENTS.md`, если он существует.

При работе с фактическим состоянием проекта приоритет имеют:

1. явные факты и исправления, данные пользователем в текущей задаче;
2. актуальный repository state и результаты реально выполненных проверок;
3. `Doc/PROJECT_STATE.md`, если он не противоречит первым двум пунктам.

`Doc/PROJECT_MEMORY.md` определяет целевую архитектуру, но не доказывает, что она уже реализована.

Не восстанавливай текущее состояние по памяти модели, если его можно проверить в репозитории. Не подменяй подтверждённое поведение предположением.

Если документация, код и фактическая проверка расходятся, не скрывай расхождение и не «исправляй» его догадкой.

## 2. Что за проект

AutoCoder — AI-first desktop-среда разработки для Windows 10/11. Центральный объект системы — пользовательская задача, а редактор, модели и инструменты являются подсистемами вокруг общего orchestration core.

Текущий стек:

- UI: React + TypeScript + Vite;
- Desktop/runtime shell: Tauri 2 + Rust;
- Editor: Monaco;
- Backend/AI services: Python;
- Local persistence: SQLite;
- Local model runtime/provider: Ollama.

Это текущие реализации, а не право сторонних компонентов владеть архитектурой. Если компонент является сменной реализацией, держи его за AutoCoder-owned interface/adapter.

Ключевые каталоги:

- `src/` — React UI, editor integration, frontend state/types/tests;
- `backend/` — Python provider/orchestration-related backend и backend tests;
- `src-tauri/` — Rust/Tauri commands, filesystem/process/persistence/runtime integration;
- `scripts/` — build/runtime helper scripts;
- `Doc/` — project memory, factual state и manual-test queue.

## 3. Архитектурные инварианты

При изменениях сохраняй направление из `PROJECT_MEMORY.md` и не пытайся реализовать всю конечную архитектуру одним PR.

Ключевые правила:

- архитектура AutoCoder принадлежит AutoCoder; сторонние SDK/runtime/protocol implementations являются сменными деталями;
- один subsystem/resource lifecycle должен иметь одного логического владельца;
- Orchestration Core является целевым владельцем task state machine;
- Rust supervisor является целевым владельцем физического lifecycle AutoCoder-owned child processes;
- Provider Runtime владеет provider semantics, но не должен становиться владельцем общей orchestration state machine;
- Workspace Transaction является целевым владельцем фактического применения AI-изменений;
- editor отображает workspace, но не заменяет его как execution backend;
- успешный Tool result не равен semantic completion пользовательской задачи;
- Persistence хранит факты/state, но не принимает business transitions;
- UI отправляет intents и отображает состояние, но не должен быть главным orchestration engine;
- Diagnostics наблюдает систему и не должна менять business semantics;
- runtime остаётся offline-first: сеть разрешена только для явно сетевых providers/capabilities.

Если код выглядит странно, сначала выясни, какой инвариант или реальная проблема привели к его появлению. Не удаляй механизм только потому, что его причина не очевидна.

Если повторяется один класс дефектов, до очередного локального патча проверь, не отсутствует ли общий contract, owner, validation boundary, diagnostics или другой фундаментальный механизм.

COMSOL — поздняя специализация. Не начинай COMSOL-specific architecture, corpus или UI, пока это не является явно текущей задачей согласно фактическому состоянию проекта.

## 4. Сторонние компоненты и заменяемость

Перед добавлением новой зависимости сначала определи, что действительно нужно:

- небольшой AutoCoder-owned модуль;
- собственная реализация публичного protocol/spec adapter;
- или изолированная сторонняя библиотека/runtime, если повторная реализация commodity-функции не даёт проекту ценности.

Не переписывай сложные parsing/indexing/runtime engines только ради отсутствия зависимостей. Если внешняя реализация полезна, изолируй её за нашим contract так, чтобы её можно было заменить без переписывания несвязанных подсистем.

Не позволяй vendor-specific types и lifecycle semantics бесконтрольно распространяться по Orchestration/UI/Persistence. Нормализуй их на boundary.

Если AutoCoder реализует собственный модуль вместо известного внешнего решения, оставь рядом с contract/module documentation короткую наводку на проверенные системы/стандарты, чьи идеи или поведение использовались как ориентир. Это reference для будущего аудита, а не разрешение копировать чужой исходный код.

## 5. Актуальность API и технических фактов

Для быстро меняющихся технологий перед написанием кода проверяй актуальную официальную документацию и конкретную используемую версию. Особенно это относится к OpenAI/Codex, GitHub, Tauri, Ollama, AI providers, interoperability protocols и COMSOL.

Не придумывай API, методы, параметры, capabilities, настройки или элементы интерфейса.

Если необходимую информацию невозможно проверить в доступной среде, не выдавай предположение за факт. В итоговом отчёте явно укажи: `Информация не проверена`.

Если пользователь сообщил фактическое состояние Windows/UI/environment, используй его как исходное условие, пока репозиторий или новая проверка не докажут обратное.

## 7. Дисциплина изменений

Сначала изучи фактический путь кода, связанные tests/contracts и текущую причину проблемы; затем меняй код.

Предпочитай минимальный **целостный** пакет изменений, а не минимальный diff любой ценой. Не трогай несвязанные файлы и не переписывай рабочий механизм без причины.

Не лечи неизвестную причину серией догадок. Если можно получить factual evidence, сначала получи его.

При cross-layer изменении сохраняй один канонический contract. Если один и тот же protocol представлен в TypeScript, Rust и Python, не допускай тихого расхождения representations.

Архитектурная миграция должна оставлять приложение в рабочем состоянии после каждого разумного этапа. Не делай giant rewrite, если существующий механизм можно перенести под новую границу ответственности.

## 8. Build и автоматические проверки

Не выдумывай команды. Если команда не перечислена ниже, сначала проверь `package.json`, `Cargo.toml`, scripts или реальную конфигурацию.

Базовая установка JS dependencies:

```bash
npm ci
```

Frontend/TypeScript/Vite:

```bash
npm test
npm run build
```

`npm run build` выполняет TypeScript build, Vite build и offline-runtime check.

Python backend:

```bash
python -m unittest discover -s backend/tests -p "test_*.py" -v
```

Rust/Tauri при изменениях Rust:

```bash
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo test --manifest-path src-tauri/Cargo.toml
```

Для отдельной проверки offline-runtime:

```bash
npm run check:offline
```

Tauri development/package commands существуют как:

```bash
npm run tauri dev
npm run tauri build
```

Packaging использует `beforeBuildCommand = npm run build` и перед bundle запускает `npm run prepare:python-runtime` через `src-tauri/tauri.conf.json`.

Правила проверки:

- сначала запускай наиболее узкие релевантные tests, затем полный affected suite;
- после executable code change запускай релевантный build/check, если среда это позволяет;
- documentation-only change не требует бессмысленного полного runtime test suite, если executable config не затронут;
- если тест невозможен из-за фактического ограничения cloud/Linux/Windows environment или отсутствующей system dependency, зафиксируй точный blocker и не маскируй его изменением production-кода;
- не объявляй Windows packaged behavior проверенным, если реально не выполнял Windows acceptance.

Если набор scripts/commands в проекте изменился, обнови этот раздел в том же PR, когда это существенно для будущих agents.

## 9. Ручные Windows-проверки

Не запрашивай ручную Windows-проверку после каждого PR.

Немедленный manual test нужен только если оставшийся непокрытый автоматикой риск в текущем изменении способен блокировать дальнейшую разработку, существенно искажать последующие результаты или ломать фундаментальный runtime/workflow.

Перед таким запросом явно оцени:

1. что уже доказано code review и автоматическими tests;
2. какой существенный риск остался;
3. почему без ручной проверки нельзя безопасно продолжать.

Остальные реально нужные проверки добавляй в `Doc/DEFERRED_WINDOWS_TESTS.md` до ближайшего readiness barrier 50/60/70/80/90/100. Не дублируй уже проверенные сценарии.

Перед barrier acceptance ревизуй очередь, удаляй obsolete/уже доказанные пункты, объединяй пересечения и формируй один copy-paste-ready сценарий. До запуска условия перечисли пользователю, что именно нужно сохранить: текст, screenshot, log или другой результат.

## 10. Git и Pull Request workflow

Repository: `iliya1947/AutoCoder`.

Не вноси task changes напрямую в `main`. Для законченного пакета создай или обнови task branch и Pull Request. Если задача уже относится к открытому PR, обновляй этот PR вместо создания параллельного без причины.

Не merge PR самостоятельно, если пользователь явно не поручил merge.

Один PR должен решать один связанный технический/документационный результат. Избегай случайных cleanup/refactor изменений вне его цели.

Перед завершением проверь diff/status и убедись, что в PR нет неожиданных файлов.

Commit messages должны быть короткими и описывать фактический результат, например `feat: ...`, `fix: ...`, `docs: ...`, `test: ...`.

Не предполагай наличие Git remote `origin` в новом cloud checkout. Если операция действительно требует remote, сначала проверь:

```bash
git remote get-url origin
```

Если `origin` отсутствует или указывает не на этот repository, исправляй его только когда это действительно требуется для задачи.

PR summary должен фактически сообщать:

- что изменено и зачем;
- какие проверки реально запущены и их результат;
- какие проверки не выполнены и почему;
- требуется ли deferred/critical Windows acceptance.

Не заявляй выполнение теста или поведения, которое не было проверено.

## 11. Project documentation

Общие правила для `Doc/` уточняются в `Doc/AGENTS.md`.

Не превращай `PROJECT_MEMORY.md` в журнал PR. Меняй его только при устойчивом изменении целевой архитектуры, фундаментальных ограничений или долгосрочных решений.

`PROJECT_STATE.md` обновляй, когда фактическое состояние проекта действительно изменилось: реализован существенный механизм, изменился milestone/status, появился подтверждённый blocker или проверка дала новый результат.

## 12. Definition of done

Задача считается законченной для coding agent, когда:

- выполнены требования текущей задачи без незапрошенного расширения scope;
- изменение соответствует фактической архитектуре и не нарушает целевые инварианты без явного решения;
- релевантные автоматические проверки пройдены либо точный environment blocker зафиксирован;
- документация состояния обновлена только там, где факты действительно изменились;
- diff не содержит случайных изменений;
- создан/обновлён соответствующий PR, если задача предполагала изменение репозитория;
- итоговый отчёт отделяет проверенные факты от непроверенного.
