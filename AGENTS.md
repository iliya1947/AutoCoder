# AutoCoder — AGENTS.md

Корневые инструкции для coding agents, работающих с репозиторием AutoCoder.

Этот файл действует на весь репозиторий. Более глубокий `AGENTS.md` может добавлять локальный контекст для своего поддерева. Явная текущая задача пользователя имеет приоритет над repository defaults, если не требует нарушить реальные platform/sandbox permissions или иные внешние ограничения среды.

## 1. Источники истины

Перед существенной задачей прочитай:

- `Doc/PROJECT_MEMORY.md` — конечная цель, целевая архитектура и устойчивые инварианты;
- `Doc/PROJECT_STATE.md` — фактически реализованное состояние, проверки, известные проблемы и текущий этап;
- релевантный более глубокий `AGENTS.md`, если он существует.

При работе с фактическим состоянием проекта приоритет имеют:

1. явные факты и исправления, данные пользователем в текущей задаче;
2. актуальный repository state и результаты реально выполненных проверок;
3. `Doc/PROJECT_STATE.md`, если он не противоречит первым двум пунктам.

`Doc/PROJECT_MEMORY.md` определяет целевую архитектуру, но не доказывает, что она уже реализована.

Не восстанавливай текущее состояние по памяти модели, если его можно проверить в репозитории. Не подменяй подтверждённое поведение предположением. Если документация, код и фактическая проверка расходятся, явно зафиксируй расхождение.

## 2. Свобода выполнения и инструменты

`AGENTS.md` задаёт цели, факты и архитектурные инварианты, но не должен искусственно ограничивать toolbox coding agent.

Используй любые доступные и подходящие инструменты, методы и источники, которые разрешены текущей средой и нужны для качественного выполнения задачи. В том числе, когда это полезно, можно использовать:

- web/internet research и официальную документацию;
- Git/GitHub и другие repository tools;
- shell, PowerShell, Python и временные scripts;
- package managers и build tools;
- code search, static analysis, linters, formatters, profilers и debuggers;
- instrumentation, logging, tracing и diagnostic/reproducer utilities;
- code generation и schema/tool generators;
- внешние development tools и protocol clients;
- создание, изменение, перемещение и удаление файлов;
- добавление, замену или удаление dependencies;
- локальные или cross-layer refactors;
- широкие архитектурные изменения, если фактический анализ показывает, что они являются лучшим решением задачи.

Списки инструментов и команд в этом файле являются справочником, а не whitelist.

Если предпочтительный инструмент недоступен, ищи эквивалентный путь вместо преждевременного отказа от задачи.

Offline-first относится к **runtime конечного AutoCoder**, а не к процессу его разработки. Coding agent может использовать сеть и внешние источники при разработке, если это разрешено средой и полезно для задачи.

Не вводи собственные запреты на действия только потому, что конкретный workflow или инструмент не упомянут в этом файле.

## 3. Что за проект

AutoCoder — AI-first desktop-среда разработки для Windows 10/11. Центральный объект системы — пользовательская задача, а редактор, модели и инструменты являются подсистемами вокруг общего orchestration core.

Текущий фактический стек:

- UI: React + TypeScript + Vite;
- Desktop/runtime shell: Tauri 2 + Rust;
- Editor: Monaco;
- Backend/AI services: Python;
- Local persistence: SQLite;
- Local model runtime/provider: Ollama.

Это **не whitelist допустимых технологий**. Компонент можно заменить, если задача или архитектурный анализ это обосновывает. При замене сохраняй AutoCoder-owned boundaries из `PROJECT_MEMORY.md`, если пользователь не принял новое архитектурное решение.

Ключевые каталоги:

- `src/` — React UI, editor integration, frontend state/types/tests;
- `backend/` — Python provider/orchestration-related backend и backend tests;
- `src-tauri/` — Rust/Tauri commands, filesystem/process/persistence/runtime integration;
- `scripts/` — build/runtime helper scripts;
- `Doc/` — project memory, factual state и manual-test queue.

## 4. Архитектурные инварианты

Сохраняй направление из `PROJECT_MEMORY.md`, но выбирай размер и форму изменения по фактической задаче, риску и проверяемости, а не по искусственному лимиту размера diff/PR.

Ключевые правила:

- архитектура AutoCoder принадлежит AutoCoder; сторонние SDK/runtime/protocol implementations являются сменными деталями;
- один subsystem/resource lifecycle должен иметь одного логического владельца;
- Orchestration Core является целевым владельцем task state machine;
- Rust supervisor является целевым владельцем физического lifecycle AutoCoder-owned child processes;
- Provider Runtime владеет provider semantics, но не общей orchestration state machine;
- Workspace Transaction является целевым владельцем фактического применения AI-изменений;
- editor отображает workspace, но не заменяет его как execution backend;
- успешный Tool result не равен semantic completion пользовательской задачи;
- Persistence хранит факты/state, но не принимает business transitions;
- UI отправляет intents и отображает состояние, но не должен быть главным orchestration engine;
- Diagnostics наблюдает систему и не должна менять business semantics;
- runtime конечного продукта остаётся offline-first, кроме явно сетевых providers/capabilities.

Если код выглядит странно, сначала выясни, какую реальную проблему или invariant он обслуживает. Не удаляй механизм только потому, что его причина не очевидна.

Если повторяется один класс дефектов, проверь, не отсутствует ли общий contract, owner, validation boundary, diagnostics или другой фундаментальный механизм.

Поэтапная миграция предпочтительна, когда она безопаснее и проще проверяется, но большой связный refactor/rewrite допустим, если фактический анализ показывает, что это лучший или необходимый путь.

COMSOL — поздняя специализация. Начинай COMSOL-specific работу только когда она действительно стала текущей задачей/этапом проекта.

## 5. Сторонние компоненты и заменяемость

Перед добавлением или заменой внешнего компонента сравни варианты по фактической задаче:

- AutoCoder-owned модуль;
- собственная реализация публичного protocol/spec adapter;
- изолированная сторонняя библиотека/runtime;
- hybrid-вариант.

Не запрещай собственную реализацию сложного parser/indexer/runtime engine заранее и не переписывай commodity engine автоматически. Сначала сравни стоимость, риск, качество, лицензии, заменяемость и долгосрочную ценность вариантов для AutoCoder.

Если внешняя реализация используется, по возможности держи её за AutoCoder-owned contract/adapter. Не позволяй vendor-specific types и lifecycle semantics бесконтрольно распространяться по несвязанным слоям.

Если AutoCoder реализует собственный модуль вместо известного внешнего решения, оставь рядом короткую наводку на актуальные reference systems/protocols, чьи идеи или поведение полезно изучать. Это reference для будущего аудита, а не обязательная dependency.

## 6. Актуальность API и технических фактов

Для быстро меняющихся технологий перед написанием зависимого от них кода проверяй актуальную официальную документацию и конкретную используемую версию. Особенно это относится к OpenAI/Codex, GitHub, Tauri, Ollama, AI providers, interoperability protocols и COMSOL.

Не придумывай API, методы, параметры, capabilities, настройки или элементы интерфейса.

Если необходимую информацию невозможно проверить в доступной среде, не выдавай предположение за факт. В итоговом отчёте явно укажи: `Информация не проверена`.

Если пользователь сообщил фактическое состояние Windows/UI/environment, используй его как исходное условие, пока новая фактическая проверка не докажет обратное.

## 7. Лицензии и секреты

Проект потенциально коммерческий.

На стадии исследования и сравнения можно рассматривать любые технические решения. Лицензионная политика ограничивает прежде всего то, что входит в production/distribution AutoCoder как dependency или bundled component.

Для распространяемых production dependencies предпочтительны permissive licenses: MIT, BSD, Apache-2.0 и совместимые permissive licenses.

Перед включением зависимости в production/distribution проверяй фактическую лицензию конкретной версии и, где существенно, транзитивные/bundled components. Лицензия протокола не означает автоматически ту же лицензию у конкретного SDK, grammar, language server, indexer, debug adapter или runtime.

GPL/AGPL или другую существенную copyleft/non-permissive runtime dependency не включай в распространяемый AutoCoder без явного решения пользователя. Это не запрещает её анализировать как reference или сравнивать с альтернативами.

Никогда не коммить secrets, API keys, tokens или credentials. `.env` допустим как локальный development override и не является целевым production Secret Store.

## 8. Дисциплина изменений

Сначала изучи фактический путь кода, связанные tests/contracts и текущую причину проблемы; затем выбирай решение.

Предпочитай целостное решение задачи. Размер diff сам по себе не является критерием качества.

Не вноси случайные изменения вне цели задачи, но меняй **все** файлы и подсистемы, которые объективно нужны для корректного решения, даже если изменение cross-layer.

Не лечи неизвестную причину серией догадок, когда можно получить factual evidence.

При cross-layer изменении сохраняй канонический contract и не допускай тихого расхождения TypeScript/Rust/Python representations.

Существующий рабочий механизм не является неприкосновенным: его можно рефакторить, заменить или удалить, если анализ показывает, что это улучшает решение и не теряет необходимые фактические свойства.

## 9. Проверки и тесты

Coding agent **самостоятельно выбирает любые тесты, проверки и диагностические методы, которые считает нужными** для конкретной задачи и риска.

Ниже приведены известные команды проекта только как удобный справочник. Они не являются обязательным набором и не ограничивают агента только этими проверками.

Известные команды:

```bash
npm ci
npm test
npm run build
npm run check:offline
npm run tauri dev
npm run tauri build
python -m unittest discover -s backend/tests -p "test_*.py" -v
cargo fmt --manifest-path src-tauri/Cargo.toml -- --check
cargo test --manifest-path src-tauri/Cargo.toml
```

`npm run build` выполняет TypeScript build, Vite build и offline-runtime check. Packaging использует `beforeBuildCommand = npm run build` и перед bundle запускает `npm run prepare:python-runtime` через `src-tauri/tauri.conf.json`.

Агент может, когда это полезно:

- запускать один test, subset, полный suite или несколько разных suites;
- создавать временные или постоянные regression/integration tests;
- писать ad-hoc reproducer/diagnostic scripts;
- применять дополнительные linters, analyzers, profilers, fuzz/property tests или другие доступные инструменты;
- выбирать иной порядок проверок;
- не запускать нерелевантные проверки, если они не добавляют достоверности текущей задаче.

Критерий — достаточная фактическая уверенность в результате, а не выполнение заранее фиксированного checklist.

Если проверка невозможна из-за фактического ограничения environment/system dependency, зафиксируй точный blocker. Не объявляй Windows packaged behavior проверенным, если реально не выполнял соответствующую Windows acceptance.

Если для проверки понадобился временный диагностический артефакт, можешь его создать; перед завершением реши по полезности, оставить его как regression/tooling или удалить как одноразовый.

## 10. Ручные Windows-проверки

Не запрашивай ручную Windows-проверку механически после каждого PR.

Немедленный manual test нужен, когда оставшийся непокрытый автоматикой риск способен блокировать дальнейшую разработку, существенно искажать последующие результаты или ломать фундаментальный runtime/workflow.

Остальные действительно полезные ручные проверки добавляй в `Doc/DEFERRED_WINDOWS_TESTS.md` до ближайшего readiness barrier. Не дублируй уже доказанные сценарии.

Перед barrier acceptance ревизуй очередь, удаляй obsolete/уже доказанные пункты, объединяй пересечения и формируй один copy-paste-ready сценарий с точными ожидаемыми артефактами результата.

## 11. Git и Pull Request workflow

Repository: `iliya1947/AutoCoder`.

По умолчанию законченные repository changes оформляй через task branch + Pull Request. Если пользователь явно выбрал другой workflow или текущая среда не позволяет выполнить GitHub write step, это не должно блокировать техническую реализацию и проверку задачи.

Если задача уже относится к открытому PR, обновляй его вместо создания параллельного без причины.

Не merge PR самостоятельно, если пользователь явно не поручил merge.

Один PR обычно должен выражать один связанный технический/документационный результат, но его размер определяется связностью решения, а не искусственным лимитом количества файлов или строк.

Перед завершением проверь diff/status и убедись, что нет случайных изменений.

Не предполагай наличие Git remote `origin` в новом cloud checkout. Проверяй/настраивай remote только когда он реально нужен операции.

PR summary должен отделять:

- что фактически изменено и зачем;
- какие проверки реально выполнены;
- что не проверено и почему;
- требуется ли отдельная Windows acceptance.

## 13. Definition of done

Задача считается законченной для coding agent, когда:

- фактически выполнена цель текущей задачи;
- выбранный объём изменений достаточен для целостного решения, независимо от числа затронутых файлов/слоёв;
- агент самостоятельно выполнил те проверки, которые считает достаточными и релевантными, либо явно зафиксировал невозможность критичной проверки;
- документация состояния обновлена только там, где факты действительно изменились;
- diff не содержит случайных изменений;
- repository workflow выполнен настолько, насколько это требуется пользователем и позволяет среда;
- итоговый отчёт отделяет проверенные факты от непроверенного.
