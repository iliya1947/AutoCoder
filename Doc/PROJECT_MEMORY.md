# AutoCoder — PROJECT_MEMORY

## 1. Назначение проекта

AutoCoder — личный проект Ильи, который в перспективе может стать коммерческим продуктом.

Главная цель проекта — создать AI-first среду разработки, способную автономно работать с программными проектами: анализировать код, создавать и изменять файлы, выполнять команды, запускать проверки, исправлять ошибки и доводить задачу до рабочего результата.

AutoCoder не должен быть просто IDE с чат-ботом. Центральным компонентом является AI-оркестратор, а редактор кода — один из инструментов системы.

## 2. Основная концепция

Целевая схема:

Пользователь
↓
AutoCoder / AI-оркестратор
↓
анализ проекта
↓
работа с файлами и кодом
↓
терминал и другие инструменты
↓
запуск / тестирование
↓
исправление ошибок
↓
готовый результат

Архитектура должна позволять подключать различные модели и инструменты без жёсткой привязки ядра к конкретному поставщику.

## 3. AI и модели

Планируется поддержка:
- облачных API-моделей;
- локальных LLM, специализированных на программировании.

Модель может выполнять роль руководителя/оркестратора или отдельного исполнителя. В будущем модели должны переключаться.

Для этого предполагается расширяемая абстракция провайдеров моделей, например `ModelProvider`.

Codex используется для разработки самого AutoCoder и не является самим AutoCoder.

Google AI Studio также рассматривается как часть AI-инструментария проекта.

## 4. Автономность и ОС

Целевая платформа:
- Windows 10/11;
- основная работа без интернета;
- интернет требуется только для облачных API.

AutoCoder является offline-first приложением и после установки должен полностью работать без подключения к интернету. UI, Monaco Editor и все его workers, JavaScript/CSS, шрифты, иконки, локализации, Python-backend, Tauri runtime resources и вспомогательные библиотеки должны поставляться локально и не выполнять runtime-загрузки из сети.

Единственное исключение — сетевые обращения к явно настроенным AI/API-провайдерам. Они выполняются только через backend/provider layer; frontend не получает произвольный внешний сетевой доступ. Локальный Ollama должен работать без интернета.

Установка build-time зависимостей (`npm`, `cargo`, `pip`) не является runtime-зависимостью установленного AutoCoder и рассматривается отдельно.

## 5. Архитектурная философия

Центральный компонент — оркестратор.

Потенциально к нему могут подключаться:
- редактор;
- терминал;
- браузер;
- Docker;
- специализированные инструменты;
- инструменты различных сред разработки.

Не требуется реализовывать всё это сразу.

Главный принцип разработки:

> Не строить всё сразу. Сделать минимальный рабочий AutoCoder как можно быстрее, но не закрывать архитектурой дорогу будущим возможностям.

Нужно проектировать только то, что необходимо ближайшему этапу, но оставлять расширяемые точки архитектуры.

## 6. MVP

Предварительный MVP должен включать:

### Интерфейс
- главное окно;
- проект / файлы;
- редактор;
- чат;
- просмотр изменений.

### Менеджер проекта
- открыть папку проекта;
- показать файлы;
- читать файлы;
- отслеживать изменения.

### Редактор
Предварительно выбран Monaco Editor.

Минимальные функции:
- открытие файлов;
- редактирование;
- сохранение;
- подсветка синтаксиса.

### AI Chat
- отправка запроса;
- получение ответа;
- история диалога.

### Context
Минимальный контекст:
- открытый файл;
- выделенный код;
- структура проекта.

### Tools

Первоначальные инструменты:

File Tool:
- читать файл;
- создать файл;
- изменить файл;
- удалить файл.

Terminal Tool:
- выполнить команду;
- получить результат.

### Diff

Изменения AI не должны безусловно применяться сразу.

Предпочтительный цикл:

AI
↓
изменения
↓
Diff
↓
подтверждение
↓
применение

### Backup

Перед изменением файлов создаётся резервная копия.

## 7. Что откладывается

На этапе MVP не требуется:
- сложная автономность на большое количество шагов;
- сложная память;
- мультиагенты;
- система плагинов;
- Git как обязательная функциональность приложения;
- LSP;
- голос;
- браузер;
- сложный планировщик;
- другие расширенные возможности.

Архитектура при этом не должна препятствовать их будущему добавлению.

## 8. Git

В источниках есть два аспекта, которые необходимо различать.

Git не должен быть обязательной зависимостью функциональности AutoCoder. Он может использоваться как инструмент разработки самого проекта.

При этом в более общей концепции AutoCoder планируется возможность работы с Git/GitHub как с инструментами разработки.

Для изменяемых файлов AutoCoder в любом случае должна существовать собственная система резервного копирования и отката.

## 9. Мультиязычность

Мультиязычность нужно учитывать с самого начала, но не обязательно полностью реализовывать в MVP.

Строки интерфейса не должны быть жёстко зашиты в компоненты.

Предварительно обсуждалась структура:

locales/
    en.json
    ru.json
    he.json

В будущем любой желающий должен иметь возможность добавить перевод и новый язык.

## 11. Первая специализация — COMSOL (только после универсального ядра)

COMSOL не является текущим этапом. Специализацию, corpus, retrieval, UI, backend logic,
knowledge engine и подготовительную инфраструктуру нельзя начинать, пока универсальное ядро
AutoCoder не будет практически завершено. Сначала закрываются базовые пользовательские workflow,
persistence/history и стабильность общего приложения.

Первой практической специализацией AutoCoder является:

**COMSOL Multiphysics 6.4.429**

Особенно:
- Java Shell;
- Methods;
- Java API.

Первая полезная версия должна хорошо помогать писать код для COMSOL Multiphysics 6.4.429.

## 12. COMSOL Knowledge Engine

Для COMSOL планируется локальная база знаний.

Источники:
- официальная документация;
- API Reference;
- Programming Reference;
- Java API;
- Java Shell;
- Methods;
- Learning Center;
- примеры;
- примеры моделей;
- успешные пользовательские проекты.

Не следует передавать LLM всю документацию целиком.

Предполагаемый процесс:

Запрос пользователя
↓
локальный поиск по знаниям
↓
релевантные фрагменты
↓
контекст проекта
↓
LLM
↓
код

Приоритет источников для COMSOL:
1. локальная документация;
2. примеры;
3. существующий рабочий код пользователя;
4. генерация LLM.

Если информации недостаточно, система должна обозначать неопределённость, а не уверенно выдумывать API.

## 13. Персональная база знаний

В будущем AutoCoder должен использовать успешные проекты пользователя.

Если уже существует рабочая COMSOL-модель, система должна иметь возможность найти похожий пример и использовать его как основу.

## 16. Безопасность

API-ключи нельзя хранить непосредственно в публичном репозитории.

Предполагается локальное хранение секретов через `.env`.

Примеры секретов:
- `OPENAI_API_KEY`;
- `GOOGLE_API_KEY`;
- `GITHUB_TOKEN`.

`.env` должен быть исключён из Git через `.gitignore`.

## 17. Проектная память

Для долговременной работы предусмотрены два разных уровня:

`PROJECT_MEMORY.md`
- постоянные сведения;
- цели;
- архитектура;
- ключевые решения;
- ограничения;
- устойчивые правила.

`PROJECT_STATE.md`
- текущее состояние;
- выполненные задачи;
- проверки;
- изменения;
- проблемы;
- текущий этап;
- ближайшая задача.

`PROJECT_MEMORY.md` меняется редко.
`PROJECT_STATE.md` обновляется при существенных изменениях состояния.

## 19. Принципы работы

- Фактическое состояние важнее памяти модели.
- Пользовательские подтверждённые данные считаются исходным условием.
- Файлы проекта и реально выполненные проверки являются источниками истины.
- При противоречиях приоритет имеет более свежая подтверждённая информация.
- Нельзя выдумывать API, команды, параметры или возможности.
- Техническую информацию нужно проверять по актуальной официальной документации.
- Если утверждение невозможно проверить: «Информация не проверена».
- Не возвращаться к завершённым этапам без причины.
- Не добавлять функции раньше времени.
- Автоматизация должна сокращать ручную работу.
- Безопасность должна быть пропорциональна текущему этапу.
- Работать последовательно, одним законченным этапом за раз.
