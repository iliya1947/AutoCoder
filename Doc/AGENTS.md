# AutoCoder — Doc/AGENTS.md

Локальные инструкции для файлов в `Doc/`. Корневой `../AGENTS.md` продолжает действовать; этот файл добавляет только правила проектной документации.

## PROJECT_MEMORY.md

`PROJECT_MEMORY.md` — архитектурная память, а не журнал разработки.

Изменяй его только когда текущая задача действительно фиксирует устойчивое изменение:

- конечной цели продукта;
- целевой архитектуры или ownership boundaries;
- фундаментального инварианта;
- долгосрочного ограничения;
- принятого архитектурного направления.

Не записывай сюда временный баг, конкретный acceptance failure, промежуточный PR status или реализацию, которая ещё не стала устойчивым архитектурным решением.

Не описывай target architecture как уже реализованную. Если точная внутренняя механика ещё требует аудита/эксперимента, оставляй её открытым архитектурным вопросом вместо выдуманного контракта.

При упоминании стороннего инструмента различай:

- AutoCoder-owned abstraction/contract;
- внешний стандарт или reference design;
- конкретную сменную implementation/dependency.

Если планируется собственный модуль вместо стороннего решения, сохраняй рядом короткую наводку на актуальные reference systems/protocols, которые стоит изучить при реализации. Не превращай reference в обязательную зависимость без отдельного решения.

## PROJECT_STATE.md

`PROJECT_STATE.md` содержит только фактическое текущее состояние.

Обновляй его после значимого изменения, если появилось новое подтверждённое состояние, например:

- механизм реально реализован/удалён/заменён;
- PR/commit действительно изменил состояние main или актуальной рабочей ветки;
- тест или Windows acceptance дал новый результат;
- milestone/status изменился;
- появился или устранён подтверждённый blocker;
- изменился фактический ближайший технический шаг.

Не записывай предположение как факт. Номера PR, commit SHA, merge status, даты, test results и другие проверяемые данные сверяй с реальным repository/tool output, когда они существенны.

Если PR ещё открыт, не описывай его изменения как уже находящиеся в `main`.

## DEFERRED_WINDOWS_TESTS.md

В очередь добавляй только ручные проверки, которые действительно нужны, но по root `AGENTS.md` не являются критическими прямо сейчас.

Перед добавлением:

- проверь, не закрыт ли риск автоматическими tests/review;
- не дублируй существующий сценарий;
- привяжи проверку к наблюдаемому поведению, а не к догадке о причине.

Перед readiness barrier:

- удалить уже доказанные пункты;
- пометить/удалить obsolete;
- объединить пересекающиеся проверки;
- оставить минимальный сценарий и точные ожидаемые артефакты результата.

## Общие правила документации

- Сохраняй подтверждённые пользователем факты, пока новая проверка их не опровергла.
- Не переписывай историю так, чтобы неудачный эксперимент выглядел успешным.
- Чётко разделяй `реализовано`, `спроектировано`, `планируется`, `экспериментально`, `не проверено`.
- Не дублируй большие блоки между `PROJECT_MEMORY.md`, `PROJECT_STATE.md` и `AGENTS.md`; каждый файл должен сохранять свою роль.
- Documentation-only PR не должен заявлять runtime implementation, которого он не содержит.
