# AutoCoder — Doc/AGENTS.md

Локальные инструкции для файлов в `Doc/`. Корневой `../AGENTS.md` продолжает действовать; этот файл добавляет только семантику проектной документации и не ограничивает доступные coding-agent tools или методы работы.

## PROJECT_MEMORY.md

`PROJECT_MEMORY.md` — **frozen architectural contract**, а не журнал разработки и не рабочий документ для постепенного уточнения реализации.

Он фиксирует:

- конечную цель продукта;
- целевую архитектуру и ownership boundaries;
- фундаментальные инварианты;
- долгосрочные ограничения;
- принятые архитектурные направления.

После финального freeze-аудита **не изменяй `PROJECT_MEMORY.md` в рамках обычной разработки** из-за bugs, implementation choices, новых providers/models/tools/protocols, refactors/rewrite, migration stages, performance work, security hardening, новых алгоритмов Council или появления более удобной сторонней реализации. Такие изменения должны укладываться в уже зафиксированные contracts/boundaries.

Если новая реализация кажется несовместимой с `PROJECT_MEMORY.md`, сначала считай это проблемой дизайна реализации и ищи решение внутри frozen invariants. Не переписывай архитектурный contract только потому, что конкретный implementation path в него не помещается.

Изменение `PROJECT_MEMORY.md` допустимо только как **явное product-level решение пользователя**, которое сознательно меняет конечную цель или фундаментальное требование AutoCoder, либо если доказано внутреннее противоречие самого frozen contract, которое невозможно устранить на уровне реализации. Предпочтение модели, новый framework или локальный bug таким основанием не являются.

Точные schemas, algorithms, storage mechanics, adapter subsets, migration order и другие вопросы, прямо оставленные в `PROJECT_MEMORY.md` как implementation-design, должны решаться **внутри** frozen invariants и сами по себе не являются основанием менять MEMORY.

Не описывай target architecture как уже реализованную. Фактическая реализация и её расхождения относятся к `PROJECT_STATE.md`, коду, tests и другим проверяемым источникам.

Временные bugs, промежуточные acceptance failures и PR status относятся к `PROJECT_STATE.md`, если пользователь не принимает новое product-level изменение самого frozen contract.

При упоминании стороннего инструмента различай:

- AutoCoder-owned abstraction/contract;
- внешний стандарт/reference design;
- конкретную сменную implementation/dependency.

Если планируется собственный модуль вместо стороннего решения, сохраняй рядом короткую наводку на актуальные reference systems/protocols, полезные для проектирования и проверки реализации. Такая наводка не делает reference обязательной dependency и не ограничивает агента только указанными вариантами.

## PROJECT_STATE.md

`PROJECT_STATE.md` содержит фактическое текущее состояние проекта.

Обновляй его, когда появилось новое подтверждённое состояние, например:

- механизм реально реализован, удалён или заменён;
- PR/commit действительно изменил актуальную ветку/main;
- test или Windows acceptance дал новый результат;
- milestone/status изменился;
- появился или устранён подтверждённый blocker;
- изменился фактический ближайший технический шаг.

Не записывай предположение как факт. Номера PR, commit SHA, merge status, даты, test results и другие проверяемые данные сверяй с реальным repository/tool output, когда они существенны.

Если PR ещё открыт, не описывай его изменения как уже находящиеся в `main`.

## DEFERRED_WINDOWS_TESTS.md

Этот файл хранит только реально полезные ручные проверки, которые разумно отложить до readiness barrier.

Coding agent самостоятельно решает, какие automated/manual/diagnostic проверки нужны текущей задаче. Этот файл не ограничивает выбор тестов и не является обязательным checklist для каждой задачи.

Перед добавлением deferred проверки:

- проверь, не закрыт ли риск уже выполненными tests/review/diagnostics;
- не дублируй существующий сценарий;
- привяжи проверку к наблюдаемому поведению и ожидаемому результату.

Перед readiness barrier:

- удалить уже доказанные пункты;
- пометить/удалить obsolete;
- объединить пересекающиеся проверки;
- оставить минимальный полезный сценарий и точные ожидаемые артефакты результата.

## Общие правила документации

- Сохраняй подтверждённые пользователем факты, пока новая проверка их не опровергла.
- Не переписывай историю так, чтобы неудачный эксперимент выглядел успешным.
- Чётко разделяй `реализовано`, `спроектировано`, `планируется`, `экспериментально`, `не проверено`.
- Не дублируй большие блоки между `PROJECT_MEMORY.md`, `PROJECT_STATE.md` и `AGENTS.md`; каждый файл должен сохранять свою роль.
- Documentation-only PR не должен заявлять runtime implementation, которого он не содержит.
- Эти правила определяют значение документов, а не запрещают агенту использовать любые доступные инструменты, источники, scripts, internet research или методы анализа, разрешённые текущей средой.
