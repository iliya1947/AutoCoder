# Проверка AI Chat в packaged Windows-сборке

Этот сценарий закрывает текущую границу Этапа 4: реальный локальный Ollama, bundled Python,
контекст редактора, предложение замены, построчный diff и lifecycle дочерних процессов.
Проверку нужно выполнять на Windows 10/11 с установленной packaged-сборкой AutoCoder.

- Lifecycle owned Ollama, external Ollama и shutdown во время запроса: **PASS**.

## Дополнительная Windows-проверка atomic Save

После сборки изменения atomic Save отдельно проверить на Windows:

1. Обычный Save заменяет destination, app-data backup содержит прежнее содержимое, а рядом
   с проектным файлом не остаются `*.autocoder-*.tmp` и `*.replaced.bak`.
2. Для диагностической сборки подменить результат Windows replacement на коды 1175, 1176
   и 1177 и проверить: Save возвращает ошибку; при 1175/1176 destination сохраняет старое
   содержимое; при 1177 старая версия восстанавливается из same-directory safety backup.
3. Имитировать ошибку восстановления после 1177: сообщение должно назвать сохранённые
   recovery paths, а код не должен удалить единственную оставшуюся старую или новую копию.

Эта проверка относится только к новому Windows atomic replacement path и не отменяет ранее
подтверждённый основной AI Chat сценарий.

## Подготовка

1. Заранее установить Ollama и модель `qwen2.5-coder:7b`.
2. Создать тестовый проект с UTF-8 файлом `chat-check.txt`:

   ```text
   Первая строка
   Вторая строка
   Третья строка
   ```

3. Отключить сеть. Не удалять модель после отключения сети.
4. Завершить все процессы Ollama и запустить установленный AutoCoder.
5. Открыть тестовый проект и `chat-check.txt`.

Перед проверкой зафиксировать среду в PowerShell, чтобы результат можно было повторить:

```powershell
Get-ComputerInfo | Select-Object WindowsProductName, WindowsVersion, OsBuildNumber
Get-FileHash "<путь к установленному autocoder.exe>" -Algorithm SHA256
ollama list
```

Не помещать в отчёт имена пользователя, полный путь к домашнему каталогу и другие
персональные данные. Для каждого раздела ниже использовать один из статусов: `PASS`,
`FAIL` или `BLOCKED`. `BLOCKED` означает, что проверка не запускалась из-за конкретного
ограничения среды, и не считается успешным результатом.

## Основной сценарий

1. Спросить: `Какой файл открыт и что находится во второй строке?`
   - Ответ должен назвать `chat-check.txt` и `Вторая строка`.
   - Во время запроса не должно появляться консольное окно Python или Ollama.
2. Выделить `Третья строка` и спросить: `Что сейчас выделено?`
   - Ответ должен опираться на выделение.
3. Снять выделение и повторить вопрос.
   - Новый запрос не должен получать ответ предыдущей ветки как историю.
4. Изменить, но не сохранять вторую строку на `Вторая строка изменена`, и спросить о ней.
   - Ответ должен учитывать несохранённый текст, а не содержимое на диске.
5. Попросить заменить открытый файл целиком, сохранив первую строку, изменив вторую и
   удалив третью.
   - AutoCoder должен показать предложение только для открытого файла.
   - Diff должен показывать неизменённую первую строку, удалённые строки до добавленных
     и корректные старые/новые номера строк.
6. Отклонить первое предложение и убедиться, что файл не изменился.
7. Повторить запрос, принять предложение и сохранить файл.
   - Перед записью должна появиться backup-копия с исходным содержимым.
   - На диске должно оказаться ровно принятое содержимое.

## Lifecycle Ollama

1. Во время двух последовательных запросов должен существовать один запущенный
   AutoCoder процесс `ollama.exe`; повторного запуска быть не должно.
2. После обычного закрытия AutoCoder принадлежащие ему `ollama.exe`, `llama-server`,
   Python и helper-процессы должны исчезнуть.
3. Повторить запуск с заранее запущенным внешним Ollama.
   - AutoCoder должен использовать его, не создавая второй процесс.
   - После закрытия AutoCoder внешний Ollama должен продолжить работу.
4. Во время запроса с принадлежащим AutoCoder Ollama закрыть приложение.
   - После закрытия не должны остаться принадлежащие приложению дочерние процессы.

## Просмотр и восстановление резервных копий

Этот уже пройденный раздел сохраняется как воспроизводимая регрессионная проверка.
Выполнять его с тем же открытым тестовым проектом в packaged Windows-приложении.

1. Создать backup существующего `chat-check.txt`: изменить файл, сохранить его и открыть
   **Резервные копии** в header.
   - Кнопка доступна только при открытом проекте.
   - Список показывает `chat-check.txt`, новые копии находятся выше старых.
   - При выборе копии справа отображается именно её прежнее UTF-8 содержимое.
2. Выбрать последнюю копию и нажать **Восстановить**.
   - На диске и в Monaco появляется показанное в preview содержимое.
   - Перед заменой текущая версия сама сохраняется как новая backup-копия.
   - Дерево проекта обновляется, восстановленный файл остаётся открытым.
3. Создать через AI новый файл `created-check.txt`, сохранить его, затем удалить через
   подтверждённое AI-предложение. Открыть **Резервные копии** и восстановить backup
   удалённого файла.
   - Файл снова появляется на диске и в дереве проекта с точным содержимым preview.
   - Восстановленный файл автоматически открывается в Monaco.
4. Проверить защиту от устаревшего состояния для существующего файла.
   - Открыть менеджер backup и выбрать копию, но до нажатия **Восстановить** изменить
     соответствующий файл внешним редактором.
   - Восстановление завершается явной ошибкой, внешнее изменение не перезаписывается.
5. Проверить защиту от устаревшего состояния для удалённого файла.
   - Открыть менеджер и выбрать backup отсутствующего файла, затем до восстановления
     создать файл с тем же именем внешним редактором.
   - Восстановление завершается явной ошибкой, внезапно появившийся файл не
     перезаписывается.
6. При несохранённых изменениях Monaco начать восстановление и отменить подтверждение.
   - Текст Monaco и файл на диске не меняются.

Фактический статус выполненной пользователем проверки: `PASS`. При будущем регрессионном
прогоне `PASS` допустим только после успешного выполнения всех шести пунктов. При `FAIL` сохранить имя файла,
выбранную дату backup, ожидаемое и фактическое содержимое и точный текст ошибки, не
включая персональные части путей.

## Lifecycle минимального Terminal Tool

Этот раздел относится к новой terminal-панели и пока не считается подтверждённым без
отдельного packaged Windows-прогона.

1. Открыть тестовый проект и выполнить короткую команду, которая печатает отдельные
   строки в stdout и stderr и завершается с ненулевым exit code.
   - Обе строки и точный exit code отображаются в панели.
   - Рабочим каталогом команды является корень открытого проекта.
   - Консольное окно `cmd.exe` не появляется.
2. Через terminal-панель запустить долгую команду, создающую дочерний процесс, и закрыть
   AutoCoder до её завершения.
   - Принадлежащие команде `cmd.exe` и все descendants завершаются вместе с AutoCoder.
3. До запуска AutoCoder отдельно запустить внешний долгоживущий процесс, не связанный с
   terminal-командой, затем повторить закрытие приложения во время команды.
   - Внешний процесс продолжает работать: общий lifecycle завершает только процессы,
     запущенные AutoCoder и назначенные его Job Object.

При проверке зафиксировать команду, созданные ею процессы и статус `PASS`, `FAIL` или
`BLOCKED`; не включать персональные части путей.

## Отдельные ошибки

После каждого подпункта вернуть изменённые файлы на место.

1. Временно переименовать `ollama.exe`: UI должен явно сообщить, что Ollama не найден.
2. Временно переименовать каталог модели: UI должен отдельно сообщить, что модель
   `qwen2.5-coder:7b` не установлена.
3. Запустить сервис, который принимает TCP-соединение на endpoint Ollama, но отвечает
   HTTP 503: AutoCoder не должен считать такой endpoint готовым.

При повторном прогоне записать дату, версию Windows, тип сборки и результат каждого раздела в
`Doc/PROJECT_STATE.md`. При сбое сохранить точный текст ошибки из UI, строку
`send_chat_message failed` из DevTools и `AutoCoder chat backend failed` из журнала
запуска. Уже подтверждённые результаты не понижать без нового фактического сбоя.

Скопировать в `Doc/PROJECT_STATE.md` заполненный блок:


Итоговый `PASS` допустим только тогда, когда все строки проверки имеют статус `PASS`.
Если хотя бы одна строка имеет статус `FAIL` или `BLOCKED`, зафиксировать её как следующий
конкретный шаг и не объявлять Windows-сценарий подтверждённым.

## Отмена отдельной команды Terminal

1. Убедиться, что локальный Ollama работает через AutoCoder, затем запустить в Terminal долгую
   команду, создающую дочерний процесс.
2. Нажать **Отменить** во время выполнения.
   - UI переходит в состояние отмены, затем показывает **Отменено**.
   - `cmd.exe` команды и все созданные ею descendants завершаются.
   - Повторное нажатие и запуск второй команды во время отмены недоступны.
3. Сразу после отмены отправить обычное сообщение в AI Chat.
   - Принадлежащие AutoCoder Ollama и Python bridge продолжают работать.
   - Новая короткая terminal-команда успешно запускается.
4. Повторить отмену команды без descendants и отмену непосредственно перед естественным
   завершением. Приложение не зависает и не завершает внешний процесс, запущенный до AutoCoder.

Зафиксировать команды, наблюдавшиеся процессы и статус `PASS`, `FAIL` или `BLOCKED`, не
включая персональные части путей. До этого прогона функция считается реализованной, но не
подтверждённой на целевой платформе.
